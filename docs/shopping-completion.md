# Завершение похода (5б)

## Хранение и восстановление

Ключи v2 остаются массивами в прежнем формате. Дополнительный ключ
`fridge.shopping-completion.v1` содержит одну незавершённую операцию:
устойчивый ID `shopping-completion:<listId>`, подтверждённые ID переносов,
исходный снимок, рассчитанный результат со стабильными новыми ID и точные
строковые before/after images трёх основных ключей.

Текущий формат журнала и операции — `version: 2`; сам ключ storage не меняется.
Операция дополнительно хранит подтверждённое ISO-время `completedAt` и упорядоченный
массив `generatedIds` — ID всех созданных продуктов, черновика и пунктов переноса.
Эти метаданные позволяют воспроизвести расчёт без выдачи новых идентификаторов.

Порядок записи: проверка целостности → журнал → повторная проверка целостности →
продукты → списки → пункты → контрольное чтение всех итоговых значений → удаление
журнала. При любом несовпадении контрольного чтения журнал не удаляется.
Это восстановимая многошаговая запись, а не атомарная транзакция трёх ключей.
Отдельного флага «остатки уже начислены» нет.

Идемпотентность обеспечивается присваиванием итоговых значений, а не повторным
прибавлением покупок. Восстановление пропускает ключи, уже равные after image.
Перед изменением любого ключа проверяются ВСЕ ключи: каждый должен совпадать
с before или after image. При посторонних изменениях восстановление блокируется.

Все обычные чтения и записи storage сначала синхронно восстанавливают журнал.
Внутри записи/восстановления нет await, поэтому в одной вкладке другой код
не может вклиниться между её шагами. Если запись или очистка журнала не удалась,
обычная работа с storage остаётся заблокированной. После перезапуска действует
тот же барьер до первого чтения для отображения. Следовательно, восстановление
не может перезаписать более новые изменения приложения: они разрешаются только
после успешной очистки журнала. Автосписание дополнительно использует синхронный
read/modify/write `updateProducts` после барьера, без устаревшего снимка.

После очистки журнала завершённый список имеет `completed`; повторное завершение
отклоняется проверкой статуса. Если журнал не удалось записать, основные ключи
не меняются и пользователь может повторить исходное подтверждение.

Неизменённые записи основных массивов берутся из исходного JSON, чтобы не
закреплять нормализацию чужих legacy записей или терять их дополнительные поля.
Для завершения используется строгое чтение: структурно повреждённые записи
не отбрасываются с последующей перезаписью уменьшенного массива.

## Строгая проверка целостности

До первой записи основных данных и до очистки выполняются следующие проверки:

1. Версия и обязательные сведения операции: устойчивый ID, целевое домохозяйство,
   каноническое ISO-время завершения, подтверждённый выбор и упорядоченные новые ID.
2. `operation.before` должен совпадать со снимком, полученным из raw before images.
   Изменение одного представления исходных данных не считается допустимой нормализацией.
3. Исходный список должен быть активным, принадлежать указанному домохозяйству
   и иметь `completedAt: null`. Исходный непустой поход должен быть обработан.
4. Чистая функция повторно рассчитывает всю операцию по before, выбору и времени.
   ID выдаются только из сохранённого массива в исходном порядке. Недостающие,
   лишние или повторные новые ID приводят к отказу.
5. Полный результат повторного расчёта должен совпасть с `operation.after` и
   всеми прочими полями операции. Таким образом проверяются статус `completed`,
   `completedAt`, неизменяемые поля списка, вся история исходных пунктов,
   начисления, новые продукты, черновик, объединение дублей и выбранные переносы.
   Неожиданные изменения чужих списков, пунктов и продуктов также отклоняются.
6. Из проверенной операции заново формируются raw after images с сохранением
   неизменённых legacy записей. Они сравниваются с записанными after images
   без нормализации полей, которая могла бы скрыть повреждение.
7. Только после этого проверяются текущие значения storage относительно before/after,
   применяются недостающие изменения и повторно читаются все итоговые значения.
   Очистка журнала разрешена лишь после точного совпадения всех трёх ключей.

При нарушении целостности восстановление отклоняется до `setItem`/`removeItem`:
основные ключи и сам журнал остаются без изменений для диагностики. Ошибка содержит
понятное русское пояснение о блокировке; успешное завершение не объявляется.
Обычные чтения/записи и автосписание продолжают блокироваться тем же барьером.

Старые журналы `version: 1`, а также записи без новых метаданных, автоматически
не применяются и не удаляются: для них нельзя доказать точность повторного расчёта.
Автоматическая миграция таких незавершённых операций не выполняется. Это ограничение
не относится к обычным данным v2 — старые продукты, списки и пункты загружаются как прежде.

Проверка выявляет внутренние противоречия; она не является криптографической защитой
от согласованной подделки всех исходных данных и метаданных сторонним кодом.

## Правила

Только обработанный непустой active текущего домохозяйства. План и факт положительны
и конечны. План сохраняется в истории. Повреждённый план можно восстановить
отдельной формой; корректные планы активного похода остаются фиксированными.
Удалённая/чужая связь, разные единицы и неоднозначные совпадения блокируют
завершение с пояснением. Автоматического преобразования единиц нет.

Недостача считается десятичной арифметикой канонических строк number через BigInt,
без фиксированного количества знаков. Разность в пределах двух относительных
машинных epsilon считается шумом. Суммы проверяются на конечность.
Реализован режим ask; AppSettings не расширен.

## Проверки отказов

Тесты моделируют исключение до и после каждого из пяти шагов, повторно подключают
mock localStorage и читают сохранённые данные заново. Проверяются единственное
начисление, один перенос, стабильность созданного продукта и отсутствие нового
эффекта после повтора. Отдельно проверены барьер при отказе, устаревшее предложение,
отказ чтения, сохранность legacy/чужих данных и восстановление перед автосписанием.

Регрессии P1 проверяют `active` в after.lists и отсутствие истории в after.items
до и после частичного применения операции. Во всех случаях проверяются нулевое
число последующих записей/удалений и дословная сохранность журнала и основных ключей.
Дополнительные тесты меняют оба представления after одновременно: неверное
начисление, факт и план покупки, время завершения, повторный продукт, перенос,
чужие данные, выбранные пункты и метаданные ID. Это проверяет повторный расчёт,
а не только равенство двух копий результата. Проверяется также отказ очистки,
если повторное чтение не подтверждает сохранённые итоговые значения.

## Ограничения

Гарантия относится к одной вкладке и перезапуску приложения. Одновременные записи
нескольких вкладок, внешняя правка localStorage и повреждение самого журнала не
восстанавливаются автоматически. При несовпадении images данные не затираются.
Журнал требует дополнительной квоты localStorage: отказ записи оставляет поход
для безопасного повтора. Общая система миграций и история в интерфейсе не добавлены.
